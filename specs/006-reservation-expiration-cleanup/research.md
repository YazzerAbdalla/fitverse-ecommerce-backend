# Research — Reservation Expiration Cleanup (Phase 5)

**Branch**: `006-reservation-expiration-cleanup` | **Date**: 2026-09-16 | **Spec**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

All `NEEDS CLARIFICATION` in Technical Context were `none` (stack: NestJS 11, TypeScript 5, PostgreSQL 17 + TypeORM, Redis 8, RabbitMQ 4, BullMQ, Jest). Spec Session 2026-09-16 resolved 5 business clarifications (Q1 60s SLA, Q2 BullMQ, Q3 RabbitMQ event, Q4 singleton, Q5 poison N-retry) that directly shape decisions below. No external technology research beyond confirming BullMQ vs `@nestjs/schedule` and RabbitMQ post-commit pattern.

## D1 — Scan predicate is `expiresAt <= NOW()` via composite index `status+expiresAt`

- **Decision**: The only eligibility query is `SELECT id FROM reservation WHERE status = 'RESERVED' AND expiresAt <= NOW() ORDER BY expiresAt ASC, id ASC LIMIT :batchSize` (FR-001). It MUST hit the existing composite `@Index(['status','expiresAt'])` on `Reservation`.
- **Rationale**: `docs/plan.md` §5.1 defines `expiresAt <= NOW()` as the authoritative rule; the worker is discovery-only. Ordering by `expiresAt` drains earliest-expiring first and gives deterministic paging; tie-break by `id` avoids non-deterministic `LIMIT` when many share same `expiresAt`. SC-008 requires `EXPLAIN` to show `Index Scan`/`Index Only Scan` on that index, not sequential scan. Test with `>=1000` rows proves index usage. No new migration — index already exists from migration `1755850000000`.
- **Alternatives considered**: (a) `SELECT ... FOR UPDATE SKIP LOCKED` scan variant → rejected as primary: it would lock rows during scan and hold them while iterating, lengthening lock window; preferred is scan **outside** per-reservation `FOR UPDATE` transaction (FR-008). SKIP LOCKED is allowed only if it still honors per-reservation `FOR UPDATE` Reservation-then-Inventories, but not required. (b) Full table scan + app-side filter → rejected: violates performance and defeats composite index.

## D2 — BullMQ as the repeat scheduler (Q2: B)

- **Decision**: Use **BullMQ** (`bullmq` + `@nestjs/bullmq`) with a `reservation-expiration` queue, `repeat`/`cron` every `30s` (default to meet **60s SLA** Q1) and `EXPIRATION_ENABLED` guard. Import via `BullModule.forRootAsync({connection: ioredis from REDIS_URL})` in `AppModule` + `BullModule.registerQueue({name:'reservation-expiration'})` in `ReservationModule`. Job `jobId` is singleton (e.g., `reservation-expiration-tick`).
- **Rationale**: Q2 clarification chose BullMQ over `@nestjs/schedule` `@Cron` after weighing durability and distribution. BullMQ persists repeat schedule in Redis, survives restarts (re-enqueued), and provides `concurrency:1` singleton (D4) needed for multi-replica deployments. `@nestjs/schedule` is in-memory only — a restart loses ticks and has no built-in distributed guard, requiring a custom Redis lock to replicate what BullMQ gives for free. Since Redis is already present (`CacheModule` + `@keyv/redis` + `ioredis`), adding BullMQ is minimal new dependency and matches `docs/plan.md` §5.4 "use existing background-job infra".
- **Alternatives considered**: (a) `@nestjs/schedule` `@Cron('*/30 * * * * *')` → rejected per Q2 B; would be simpler but not persistent and would need an extra Redis lock for singleton. Kept as possible future simplification if BullMQ proves heavy, but not chosen. (b) RabbitMQ delayed job → rejected: RabbitMQ is not a scheduler; implementing repeat via TTL/delay complicates and adds no benefit over BullMQ's native `repeat`. (c) No scheduler, manual `POST /reservations/:id/expire` only → rejected: violates Phase 5 exit criterion "eventually release".

## D3 — Per-candidate transactional path reuses Phase 4 helper (`FOR UPDATE` Reservation-first + sorted Inventories)

- **Decision**: For each candidate `reservationId` from the scan, execute `dataSource.transaction(async manager => { await reservationExpirationService.expireOne(manager, id) })` where `expireOne` is a thin wrapper around the existing `ReservationService.transitionWithInventoryInternal(manager, null, id, EXPIRED, undefined, undefined, false)` — i.e., `FOR UPDATE` Reservation (without `relations` outer join, `pessimistic_write`), then verify `status===RESERVED` (idempotent skip if not), load `items`, verify `Inventory` rows exist, `FOR UPDATE` `Inventory` rows in sorted `inventoryId` order, `reservedAmount -= qty` (stock unchanged), `status=EXPIRED`, save.
- **Rationale**: Reuses the Phase 4 code path that already implements deterministic lock ordering, `CHECK`→`409` mapping, and idempotent `COMPLETED→COMPLETED` logic — but for expiration the idempotent case is `status != RESERVED` after lock → skip (FR-005). Keeps DRY, guarantees identical inventory semantics for manual `PATCH /:id/expire` (immediate override) and worker `expiresAt <= NOW()` scan path; only difference is scan predicate (FR-004). Short transaction (D7) holds locks only for the integer mutation, no external I/O.
- **Alternatives considered**: (a) Duplicate expiration logic in new service → rejected: would diverge semantics and risk double-release bugs. (b) Single transaction for entire batch (`FOR UPDATE` on all reservations + all inventories) → rejected: long hold, unbounded memory, deadlocks; spec FR-007 requires per-reservation transactions with batch-continue-on-failure.

## D4 — Multi-replica safety: BullMQ singleton + `FOR UPDATE` as correctness backstop (Q4: B)

- **Decision**: Guarantee single-winner via **two layers**: (1) **efficiency** — BullMQ singleton repeat job (`jobId: 'reservation-expiration-tick'`, `removeOnComplete`, `concurrency:1` on `@Processor('reservation-expiration')`, and `BullModule` repeat deduplication) ensures only one replica enqueues/processes a given tick. (2) **correctness** — `FOR UPDATE` on `Reservation` row remains the authoritative serialization; if singleton is bypassed (e.g., two ticks race or manual test calls `processExpiredBatch` directly), the DB lock still ensures only one transition `RESERVED→EXPIRED` succeeds and the loser detects `status != RESERVED` and skips.
- **Rationale**: Q4 B clarification. Singleton eliminates wasteful duplicate scans in multi-replica deployments; `FOR UPDATE` eliminates correctness reliance on Redis. Advisory locking alone would be redundant and would make correctness depend on Redis availability — rejected per constitution I. The combination matches spec Edge Case "two replicas" and FR-006 single-winner requirement.
- **Alternatives considered**: (a) `FOR UPDATE SKIP LOCKED` scan as sole guard → rejected: not needed when singleton already deduplicates; it also complicates ordering. (b) Pure `FOR UPDATE` without singleton → would work correctness-wise but cause redundant work and duplicate RabbitMQ publishes under replicas; rejected per Q4 B efficiency.

## D5 — RabbitMQ `reservation.expired` post-commit event (Q3: C)

- **Decision**: After each successful per-reservation `COMMIT` (inside the loop, outside the transaction), inject `NOTIFICATION_SERVICE` (`ClientProxy` from `ClientsModule` already in `AppModule`) and `client.emit('reservation.expired', {reservationId, userId, expiredAt, inventoryIds, expiredAt: new Date().toISOString()})` (or `client.send` per existing `notification_queue` pattern). Wrap in `try/catch`, log `error` on publish failure, **do not roll back**. No transactional outbox in Phase 5; at-most-once publish is acceptable (retry of publish is not required to satisfy SCs). Broader Phase 11 fan-out (email, analytics) remains out of scope.
- **Rationale**: Q3 C clarification. Publishing after commit follows `docs/architecture/inventory-reservation.md` "publish RabbitMQ events *after* the DB commit" and constitution Additional Constraints "async failures MUST NOT roll back". Using existing `NOTIFICATION_SERVICE` RMQ transport (`Transport.RMQ`, `urls:[RABBITMQ_URL]`, `queue: notification_queue`) avoids new infra. Keeping publish per-reservation (not batch) keeps transactions short and isolates publish failures to that reservation only.
- **Alternatives considered**: (a) Silent (no event) → rejected per Q3 C. (b) BullMQ job instead of RabbitMQ → rejected: product explicitly chose RabbitMQ for domain event, BullMQ is for scheduling. (c) Outbox + retry → rejected: adds PG table and is Phase 12 reliability work, not needed for "eventually release" correctness.

## D6 — Batch paging and non-overlapping ticks

- **Decision**: The exposed service method is `processExpiredBatch(limit = EXPIRATION_BATCH_SIZE)` that: (1) `SELECT id FROM reservation WHERE status='RESERVED' AND expiresAt <= NOW() ORDER BY expiresAt ASC, id ASC LIMIT :limit` **without** `FOR UPDATE`, (2) loops candidates sequentially, each in its own `dataSource.transaction` via `expireOne(manager, id)` (D3), catching per-candidate errors, counting `scanned/expired/skipped/failed/retried`, logging per spec FR-009, publishing RabbitMQ after commit, (3) returns summary. The BullMQ processor `handleRepeat` calls `processExpiredBatch(EXPIRATION_BATCH_SIZE)` once per tick; a `processAll` helper optionally loops `while (scanned>0) await processExpiredBatch` for tests that need draining 25 rows with `batchSize 10`. Tick guard: BullMQ `concurrency:1` + optional in-memory `processing` flag to skip if previous tick still running (non-overlapping, FR-002).
- **Rationale**: Batching via `LIMIT` + ordered scan keeps each transaction short and avoids loading all expired rows into memory (FR-008). Per-reservation transactions isolate failures (FR-007). Non-overlapping prevents lock stampede when a slow batch exceeds 30s. Draining `processAll` is for integration test convenience, not for production tick (tick processes one batch per interval, eventually draining across ticks SC-007).
- **Alternatives considered**: Single transaction for whole batch → rejected (long lock). `SKIP LOCKED` for parallel workers → not needed with singleton, adds complexity.

## D7 — Poison handling: `EXPIRATION_MAX_RETRIES=3`, log every retry, then skip (Q5 custom)

- **Decision**: Maintain an in-memory or lightweight persistent retry counter per `reservationId` (simplest: `Map<id, count>` in service, or reuse BullMQ job attempts). On per-candidate failure due to `CHECK` violation (`23514`/`CHK_`) or `Inventory not found` (`404`), increment counter, log `warn`/`error` with `reservationId` and `attempt/N`, rethrow to be counted as `failed` for that tick but **do not mark EXPIRED**. On next tick the same poison candidate will be scanned again (still `RESERVED` and `expiresAt <= NOW()`) and retried. After `EXPIRATION_MAX_RETRIES` (env `EXPIRATION_MAX_RETRIES`, default `3`, configurable 1-10) failures for the same `reservationId`, the service skips further automatic retries for that `id` until manual intervention or data fix (candidate remains `RESERVED` but is filtered out via service-side `skipSet` or BullMQ `failed` queue). Every retry and skip is logged (`warn` retry, `error` final skip). Batch always continues to next candidate.
- **Rationale**: Q5 custom "retry N then skip and log every retry" balances at-least-once (transient DB contention or concurrent winner may succeed on next tick) with protection against tight-loop spam on persistent constraint violation. Default `3` is the same as OTP retry precedent in specs and minimizes log noise while allowing transient contention to resolve. Leaving poison as `RESERVED` (not forcing `EXPIRED` with clamp) preserves invariant `reservedAmount>=0` — forcing would hide data corruption. Logging every retry satisfies observability.
- **Alternatives considered**: (a) Retry indefinitely each tick → rejected per Q5 custom; would spam logs and never quarantine persistent poison. (b) Force `EXPIRED` with clamp (`reservedAmount = max(0, reservedAmount - qty)`) → rejected: would mask corruption and violate `reservedAmount -= qty` exactly-once semantics. (c) Skip permanently without retry → rejected: would hide transient DB contention that could self-heal.

## D8 — Testing strategy: real PostgreSQL for consistency, `EXPLAIN` for index, mocks for queues

- **Decision**: Unit tests mock `DataSource`/`EntityManager`/`Bull`/`ClientProxy` to cover predicate builder, `validateTransition`, idempotent skip, `EXPIRATION_MAX_RETRIES` branching, and singleton guard. Integration tests against **real PostgreSQL** (docker, `--runInBand`) cover: (a) expired `RESERVED` → `EXPIRED` with `reservedAmount` release, (b) not-yet-expired not selected, (c) multi-item atomic, (d) concurrent `worker vs complete` / `worker vs cancel` / `worker vs worker` single-winner (real `DataSource.transaction`, `Promise.all`), (e) idempotency (second worker tick no double-release), (f) batch paging (`batchSize 10` drains 25), (g) `CHK` failure single-candidate rollback + retry N + batch continue, (h) `EXPLAIN (ANALYZE, BUFFERS)` shows `Index Scan` on composite index, (i) RabbitMQ publish mock called after commit, (j) scheduler actually fires with `EXPIRATION_INTERVAL_MS=5000` fake timers or real short interval.
- **Rationale**: Constitution VII mandates DB-backed tests for transactions/locking; `FOR UPDATE` single-winner cannot be proven via mocks. `--runInBand` avoids parallel Jest workers sharing one DB (observed 89/89 stable vs flaky in Phase 3). `EXPLAIN` test is the measurable proof for SC-008; may be tagged `@integration` and skipped if `EXPLAIN` not permitted. RabbitMQ/BullMQ mocked keeps tests hermetic; integration with real Redis/RabbitMQ is optional.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| BullMQ repeat schedule lost on Redis flush | Persist repeat in Redis with `jobId` singleton; on startup re-register `repeat` in `Processor.onModuleInit`; scan still works manually via `processExpiredBatch` even if scheduler absent |
| `FOR UPDATE` deadlock on multi-item reservations with opposite `inventoryId` order | D3 sorts `inventoryIds` lexicographically ascending (same as Phases 3-4) — deterministic lock ordering |
| `CHK_reservedAmount` violation mapped as `500` instead of `409` | Catch `QueryFailedError` code `23514`/`CHK_` and rethrow `ConflictException` per `reservation.service.ts:400-412` pattern |
| RabbitMQ publish failure after commit causes event loss | Logged `error` with `reservationId`; not rolled back; Phase 12 outbox can be added later if at-least-once broadcast is required — acceptable for Phase 5 "eventually release" SLA |
| Tick duration exceeds `30s` interval | BullMQ `concurrency:1` + in-memory guard skips if previous tick still running; batch `LIMIT` keeps per-tick work bounded |
| Poison candidate spam loop | D7 `EXPIRATION_MAX_RETRIES=3` quarantine after N failures, log every retry, batch continues |
| Parallel Jest workers pollute DB across suites | `npm run test -- --runInBand` documented in `quickstart.md` |
