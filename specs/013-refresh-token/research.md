# Research — Refresh Token Rotation — Phase 17

**Feature**: `013-refresh-token` | **Date**: 2026-09-23 | **Spec**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

All `NEEDS CLARIFICATION` in Technical Context were `0`; the 10 business clarifications in `spec.md §Clarifications` (5 kickoff + 5 session 2026-09-23) are inputs. Below are the 8 research decisions that resolve unknowns and justify Phase 17 choices.

---

## D1 — Opaque random `RefreshToken` (`crypto.randomBytes(32)`+`sha256`) vs JWT `refresh_token` with `jti`

- **Decision**: Opaque random `raw = crypto.randomBytes(32).toString('hex')` (`64` hex, `256` bits), store `tokenHash = sha256(raw)` + `expiresAt=now+REFRESH_TOKEN_TTL(7d)` in PG `RefreshToken`. Never store or log `raw`. Alternative JWT self-contained `refresh_token` with `jti` + DB `jti` table rejected.
- **Rationale**: Selective revocation without global `tokenVersion++` nuke — each `POST /auth/logout {refreshToken}` can revoke single hash; single-use rotation (`revokedAt` on `refresh`) allows theft detection reuse→revoke-all. Matches existing `PasswordResetToken` pattern (audited Phase 16) so reuse `crypto`+`sha256`+`FOR UPDATE` code. JWT `jti` would add `jsonwebtoken.verify` path + `tokenVersion` coupling and still need DB row for revocation, so opaque is simpler with lower audit surface.
- **Alternatives considered**: JWT `refresh_token` (`sign {sub, jti, tokenVersion} 7d`, store `jti` hash) — rejected: cannot selectively revoke without `tokenVersion++` or per-`jti` table equal complexity but adds JWT expiry verification + key rotation. Session-id `uuid` without hash — rejected: stores raw-equivalent `uuid` in DB leak would be bearer; `sha256` hash mitigates DB dump replay.

## D2 — Single-use rotation (`revokedAt` on `refresh` + new row) vs sliding reuse (extend `expiresAt`)

- **Decision**: Single-use rotation per FR-003: `refresh` inside `dataSource.transaction` does `UPDATE old SET revokedAt=NOW()` + `INSERT new {userId, tokenHash=sha256(newRaw), expiresAt=now+7d}` + `sign new accessToken`. Reuse of old hash → `401` + theft revoke-all (`UPDATE ... WHERE userId=:id AND revokedAt IS NULL`).
- **Rationale**: Prevents replay if `refreshToken` leaks from client storage/logs; second use is definitive theft signal per `docs/plan.md` §17.5. Transaction `FOR UPDATE` on `RefreshToken` serializes `Promise.all([refresh,refresh])` single-winner. Sliding reuse (no `revokedAt`, just `expiresAt+=7d`) would be idempotent but would not detect theft and would allow stolen token to live 7d longer each use.
- **Alternatives considered**: Sliding-window `UPDATE expiresAt = NOW()+7d` where `tokenHash` stays active — rejected: loses theft detection, complicates `429` per-hash bucket (hash persists). Keep-old-and-add-new without `revokedAt` (multi-active, no rotation) — rejected: table bloat + no single-use revocation.

## D3 — Dual transport (body `refreshToken` + `HttpOnly` cookie `refresh_token`) vs `Authorization: Bearer` header

- **Decision**: Dual per FR-008 (clarification Q dual A): return `refreshToken` in both `Set-Cookie: refresh_token=<raw>; HttpOnly; Secure=<secure>; SameSite=Strict; Path=/auth; Max-Age=<ttlSec>` and JSON `{refreshToken}` on `login`/`refresh`; accept either `Body.refreshToken` (precedence) or `Cookie.refresh_token` (`req.cookies[REFRESH_TOKEN_COOKIE_NAME]` via `cookie-parser`) on `POST /auth/refresh`/`logout`, if both missing → `401`. Swagger documents `Refresh via Cookie or Body`.
- **Rationale**: Browser SPA can rely on `HttpOnly` cookie (not accessible to XSS JS) while `supertest`/Postman/mobile can use JSON body; `Authorization: Bearer <refreshToken>` would collide with `accessToken` Bearer and require separate header `X-Refresh-Token`. Cookie `Secure` is `ConfigService REFRESH_TOKEN_COOKIE_SECURE === 'true'` (prod `true`, dev `false` when `NODE_ENV !== 'production'`), `Path=/auth`, `Max-Age=604800`. `cookie-parser` `app.use(cookieParser())` before `ValidationPipe` populates `req.cookies`; fallback `req.headers.cookie` parsing if middleware missing.
- **Alternatives considered**: Body-only — rejected: forces SPA to store `refreshToken` in `localStorage` (XSS exfiltratable). Cookie-only — rejected: `supertest` must parse `set-cookie` and non-browser clients would need `Cookie` header manual. Header `X-Refresh-Token` — rejected: non-standard, no `HttpOnly` protection.

## D4 — Theft detection: `401` + bulk revoke-all vs `401` only (log-only)

- **Decision**: On `revokedAt NOT NULL` reuse (already rotated/used), return `401 Invalid or expired refresh token` **and** execute `UPDATE RefreshToken SET revokedAt=NOW() WHERE userId=:userId AND revokedAt IS NULL` + `Logger.warn refresh reuse theft detected userId=:id hashPrefix=:prefix slice(0,6)` + optional `CACHE_MANAGER INCR idempotency:duplicate:skipped:refresh EX 86400` per FR-003 clarification Q theft A. On `not found` or `expiresAt <= NOW()` → `401` **without** bulk revoke (no `userId` to target).
- **Rationale**: Reuse of single-use token is high-confidence theft (rotation should have invalidated old hash immediately); nuking all remaining sessions forces attacker and legitimate user to re-login, limiting blast radius. Reuse after `logout` is also covered (old hash `revokedAt` → same branch). `not found` without user linkage would cause spurious nuke if attacker guesses random hash.
- **Alternatives considered**: `401` log-only no revoke — weaker, stolen `r2` (other device) would remain valid after `r1` theft. Immediate `tokenVersion++` on theft — overkill, would also nuke `accessToken`s but `RefreshToken` bulk revoke already suffices and `tokenVersion` nuke reserved for `logout-all`/`reset-password` explicit user action.

## D5 — `User.tokenVersion` reuse vs per-`RefreshToken` version column

- **Decision**: Reuse existing `User.tokenVersion int default 0` (Phase 16 `1755900000000-AuthUpgradesUserAndResetToken`) as global revocation nuke per FR-006. `JwtStrategy.validate` already checks `payload.tokenVersion === user.tokenVersion else 401`. `RefreshToken` rotation embeds current `user.tokenVersion` into new `accessToken` (`JwtService.signAsync {sub,email,fullName,role,tokenVersion:user.tokenVersion}`). Bulk `UPDATE RefreshToken SET revokedAt=NOW() WHERE userId=:id AND revokedAt IS NULL` is explicit on `logout-all`/`reset-password`; `tokenVersion` increment is the guard that makes old `accessToken` fail `JwtGuard`.
- **Rationale**: No schema change to `User` beyond Phase 16; reuse proven `reset-password` `tokenVersion++` pattern (audit `src/modules/auth/auth.service.ts:202` `tokenVersion: () => '"tokenVersion" + 1'`). Adding `refreshTokenVersion` column would duplicate invariant and require second `JwtStrategy` check. Simplest: `refresh` with `userId` lookup fails if row already `revokedAt` after `tokenVersion++` bulk revoke, so theft path already 401.
- **Alternatives considered**: New `User.refreshTokenVersion int` — rejected: two version columns, more `ConfigService` complexity, no benefit since `tokenVersion` already covers all `accessToken`s. Store `tokenVersion` snapshot per `RefreshToken` row and compare `row.tokenVersion !== user.tokenVersion → 401` — optional but redundant with bulk revoke; kept as optional check but primary is `revokedAt IS NULL`.

## D6 — Cap 5 active LRU vs unbounded vs cap 10

- **Decision**: Cap 5 active `RefreshToken` per user per clarification Q2 C: on `login` or `refresh` creation when `SELECT count(*) WHERE userId=:id AND revokedAt IS NULL` `>=5`, revoke oldest `SELECT id FROM refresh_token WHERE userId=:id AND revokedAt IS NULL ORDER BY createdAt ASC LIMIT 1 FOR UPDATE` → `UPDATE SET revokedAt=NOW()` before `INSERT new`. Eviction inside same `DataSource.transaction` (or at least atomic `UPDATE`+`INSERT`) with `FOR UPDATE` on oldest row to avoid race.
- **Rationale**: Bounds table growth from automated login retries/timeout double-login (edge `login` retry after commit but before JSON reached client would create 2 active rows per attempt); 5 supports phone+laptop+tablet+browser+one spare, matches typical SaaS device limit. 10 would allow more but increase storage; unbounded would grow linearly with buggy clients. 5 is stricter and matches Interview Service `5` pattern.
- **Alternatives considered**: Unbounded A — rejected: no bound, `reset-password` bulk revoke would leave many rows, purge `7d` would retain but active set could be large. Cap 10 B — acceptable but 5 chosen as tighter; easy to bump via `ConfigService REFRESH_TOKEN_MAX_ACTIVE=5` without code change if product requests 10.

## D7 — Rate limiting dual buckets `10/h IP` + `5/h per tokenHash 6-prefix` vs IP-only vs user-based

- **Decision**: Dual per clarification Q3 B and FR-007: `RateLimitGuard` enforces two `CACHE_MANAGER INCR+EXPIRE` buckets for `POST /auth/refresh` — `rl:POST /auth/refresh:ip:<ip> → 10/3600` + `rl:POST /auth/refresh:hash:<6prefix> = sha256(raw).slice(0,6) → 5/3600`; either exceeding → `429` with `Retry-After: 3600` + `X-RateLimit-Limit/Remaining` before `DataSource.transaction` (guard outermost). `POST /auth/logout` `20/h IP`, `POST /auth/logout-all` `10/h user` (`req.user.sub ?? ip`), all `ConfigService` `REFRESH_RL_*` clamped `>=60000` else fallback + `Logger.warn`, fail-open on `CACHE_MANAGER throw`.
- **Rationale**: IP bucket mitigates brute-force enumeration across hashes; per-hash bucket mitigates stolen-token hot-loop from single attacker or distributed IPs. `6-prefix` balances granularity (full `64` hash key would be large, `6` enough to bucket per token family without PII). Reuse existing `RateLimitGuard` distributed `createKeyv REDIS_URL` `rl:*` pattern from Phase 10 (same as `POST /auth/login` `10/h`). Dual is defense-in-depth since theft revoke-all already mitigates reuse but rate-limit adds pre-`FOR UPDATE` gate.
- **Alternatives considered**: IP-only A — weaker against distributed attack. User-based C (`req.user.sub` when identifiable) — not applicable for `refresh` (public, no `JwtGuard`), but `logout-all` already uses user bucket; `refresh` cannot rely on `sub` because `refreshToken` hash not yet mapped to `userId` before rate-limit (would need DB lookup before guard, violating outermost rule).

## D8 — Purge retention `7d` vs `30d` vs never, and `emailVerified` refresh gate `allow+warn` vs block

- **Decision**: Purge `7d` after `expiresAt` or `revokedAt` per clarification Q4 B: nightly job (BullMQ repeat or `setInterval` or manual query) `DELETE FROM refresh_token WHERE (revokedAt IS NOT NULL AND revokedAt < NOW() - INTERVAL '7 days') OR (revokedAt IS NULL AND expiresAt < NOW() - INTERVAL '7 days')`. `X-Email-Unverified` per Q5 C: `refresh` with `user.emailVerified=false` still succeeds `200` but `Logger.warn refresh unverified email userId=:id emailPrefix=:prefix` and `res.setHeader('X-Email-Unverified','true')` for observability; client may prompt verification.
- **Rationale**: `7d` matches `REFRESH_TOKEN_TTL=7d` window so audit retains exactly one TTL beyond expiry/revocation for forensics, tighter than `30d` but longer than immediate. Bulk `7d` keeps `DELETE` small; `30d` would retain more but increase table scan. Never-purge would grow unbounded. Unverified-email allow+warn preserves session continuity (login already succeeded without verification gate) while surfacing signal; blocking `403` would force re-verification loop breaking mobile UX, but header allows future strict mode toggle.
- **Alternatives considered**: `30d` A — acceptable but looser, more storage; chosen `7d` as minimal audit. Never C — rejected: table grows without manual intervention. Block if unverified B — rejected: `register`→`login` currently allows unverified (Phase 16 `emailVerified` not enforced), so `refresh` must be consistent.
